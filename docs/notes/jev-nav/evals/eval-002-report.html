Why Mode 3 lost on nav-fleet

Three causes, one of them in our eval

Jev over-selects

"Relevant" is too loose a question

Luna's intents named 2–3 bindings, yet Jev said yes to 6–53 of the 61. Precision across the run was 6%. "Is this relevant?" invites yes for anything related.

Try: ask "must this binding be read or changed to do the intent?", raise the yes threshold, and open bindings the intent names by exact path without asking Jev.
View churn

Every call replaces the whole view

The planner used modify_view like expand, one target at a time, so each call dropped what it had just opened: 18 calls and 6 more turns than control.

Try: make modify_view add to the current view by default and fold only on a new focus, and tell the planner to ask for everything at once.
Eval design

The task names the answer

The prompt names fuel_cost, idle_penalty and needs_service, so control found all three with three expand calls. Navigation was never hard; Jev could only add cost.

Try: describe symptoms ("the report overcharges idle trips") and let the agent locate the cause, as in symptom-to-cause localization benchmarks.
Jev cost

Not free at this size

Each selection sent all 61 bindings' code, about 11k tokens: $0.0083 over 18 calls, 24% of the run.

Try: send one-line heads for bindings far from the intent and full code only for candidates.
