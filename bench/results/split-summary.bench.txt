  Built to separate aM from aPL, which none of the other tasks do.
  
  The program routes three expensive aggregates through a single tuple 
  binding, destructures it, and then spends most of its time in three `grade` 
  calls that each depend on exactly ONE component of that tuple. Editing one 
  component gives aPL nothing: without tuple flags a tuple's value is clean 
  or dirty as a whole (IncrEval.exp_flag returns Dirty when the expression 
  itself was not re-used), so all three destructured variables go dirty and 
  all three grades are recomputed. aM implements section 8's Pair rule -- 
  `norm`/`split` give one flag per component, and a tuple PATTERN distributes 
  them positionally -- so the two untouched components stay clean and only 
  one grade re-runs.
  
  On the synthetic trace of four single-component edits (5 reps): a0 1827ms, 
  aPL 1005ms (0.550), aM 471ms (0.258), a2 1184ms (0.648), aStar 501ms 
  (0.274). aM is about 2.1x faster than aPL, and aStar matching aM confirms 
  the win comes from tuple_flags alone -- a2 adds nothing here because the 
  expensive work already sits in top-level bindings. Per-step the gap is 
  steady rather than driven by one outlier: aM 105-136ms against aPL 
  239-275ms on the four edits, with tight IQRs.
  
  Two constraints shaped the design. The first is that only TUPLES carry 
  componentwise flags: IncrEval's pattern walk sends `ListLit` and `Cons` 
  through `opaque`, which collapses a component flag to Dirty. 
  bench/traces/split-summary-list.json is the control for exactly this -- the 
  same program with the statistics in a list and a `let [a, b, c] = summary` 
  pattern, edited identically, reaching the same value. There aM's advantage

  only about 1.15x faster than aPL instead of 2.1x. Treat that residue as 
  noise rather than a small real effect -- an earlier 3-rep run of the same

  list gets essentially no aM benefit.
