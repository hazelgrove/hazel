Hazel-Native Normalization and Proof Export Plan

The goal is to validate written proof steps without trusting a CAS simplification. Hazel should decide equivalence using a small, inspectable normalizer and, when possible, produce a proof trace that can be exported to a theorem prover.

No CAS trust boundary Avoid accepting a black-box simplify step that cannot be reconstructed by the theorem prover.
Normalize to decide Use canonical forms to determine whether two expressions represent the same arithmetic expression.
Trace to export Record small rewrite steps so the checker result can become theorem prover evidence.

Problem

A CAS can validate examples like 3 + x = x + 3, but it does so by returning a large simplification result. That is useful for a UI check but too coarse for a theorem prover export pipeline. The exported proof would either need to trust the CAS or re-prove a hidden simplification.

The important distinction is: normalizing for equality is not enough. For export, normalization must either be trusted by the target theorem prover or accompanied by a derivation that the target can replay.

Plan A: Hazel-Only Symbolic Normalizer

The first step is to replace Algebrite for simple symbolic arithmetic with a Hazel-native normalizer. This normalizer should start small and be intentionally scoped.

Affine Normal Form

Start with linear arithmetic over constants and symbolic terms: 

type atom =
  | Const(Bigint.t)
  | Sym(string)
  | Other(Exp.t);

type affine = {
  constant: Bigint.t,
  terms: list((atom, Bigint.t)),
};

Examples:

  • 3 + x normalizes to constant 3 and term 1*x.
  • x + 3 normalizes to the same form.
  • x + x + 3 normalizes to constant 3 and term 2*x.
  • 2 * x + 3 can normalize to constant 3 and term 2*x.

Canonicalization Rules

  1. Flatten addition and subtraction.
  2. Fold numeric constants.
  3. Recognize constant-times-symbol where easy.
  4. Combine like symbolic terms.
  5. Drop zero coefficients.
  6. Sort symbolic terms by a stable expression key.
  7. Compare canonical forms structurally.
This handles common classroom steps such as 3 + x to x + 3, 1 + 2 + x to x + 3, and x + x to 2 * x without any external solver.

Scaling Beyond Affine Arithmetic

When the examples require multiplication of symbolic expressions, move from affine form to polynomial form. 

type monomial = list((atom, int));     /* x^2 * y */
type polynomial = list((monomial, Bigint.t));

This supports:

  • x * 3 = 3 * x
  • (x + 1) * (x + 2) = x^2 + 3*x + 2
  • commutativity and associativity of multiplication
  • distributivity when expansion is enabled

This should still be domain-specific, not a general-purpose theorem prover. The normalizer should only implement algebraic laws that Hazel can also emit as proof steps.

Plan B: Normalization With Proof Traces

For theorem prover export, the checker should return more than valid. It should return the canonical forms and a replayable list of trusted rewrites. 

type rewrite_rule =
  | AddComm
  | AddAssoc
  | AddIdentity
  | AddConst
  | MulComm
  | MulAssoc
  | MulDistrib
  | MulIdentity
  | MulConst;

type rewrite_step = {
  before: Exp.t,
  after: Exp.t,
  rule: rewrite_rule,
};

type check_result = {
  justification: string,
  normalized_left: Exp.t,
  normalized_right: Exp.t,
  proof_steps_left: list(rewrite_step),
  proof_steps_right: list(rewrite_step),
};
Normalize left Rewrite e1 to a canonical expression while recording each small rule application.
Normalize right Rewrite e2 to a canonical expression with its own trace.
Compare Check that the two canonical expressions are syntactically equal.
Export Emit e1 = nf, e2 = nf, then combine by symmetry and transitivity.

Short-Term Coq Export Fallback

A practical interim fix is to let generated Coq lemmas use arithmetic automation such as ring for simple integer arithmetic obligations. This is better than using cbv; reflexivity, because unfolding Z.add can produce large pattern-match terms that are extensionally equal but not definitionally identical.

This fallback should not become the trusted proof story. It proves that Coq can solve the generated arithmetic equality, but it does not explain the user's written Hazel step as a replayable sequence of Hazel rewrite rules.

The intended use is therefore:

  1. Use ring as a compatibility fallback so exported files are not broken while the normalizer is still coarse.
  2. Continue developing Hazel-native normalization with explicit proof traces.
  3. Prefer trace export whenever a checker can explain the step with known rules.
  4. Keep theorem prover automation as a fallback or diagnostic aid, not as the primary acceptance criterion for exportable written steps.

Checker API Direction

The current branch already has an extensible checker shape. The next design step is to evolve it from returning just a justification string to returning a structured result.

Current role Proposed role
normal_form decides equality. normal_form plus proof trace decides and explains equality.
checker.justification is a short label. check_result carries a theorem-prover export payload.
Algebrite can check arithmetic equivalence. Hazel-native rules check only what can be exported.

Recommended Implementation Path

  1. Keep the checker interface, but add a richer check_result type.
  2. Implement affine arithmetic normalization in Hazel.
  3. Make each normalization transformation record a rewrite_step.
  4. Export the trace as theorem-prover steps using known lemmas for associativity, commutativity, identity, and constant arithmetic.
  5. Add polynomial normalization only when examples require symbolic multiplication or distribution.
  6. Remove or demote Algebrite from trusted written-step validation. It may remain as a suggestion/debug aid, but not as the acceptance criterion for exportable proof steps.

Open Design Questions

  • Should normalization preserve the user's intermediate expression as a single proof step, or expand it into multiple hidden/exported theorem-prover steps?
  • Which arithmetic laws are already available in the target theorem prover export, and which need to be generated as lemmas?
  • Should exercises be able to restrict which checker domains are accepted?
  • How should Hazel display a broad normalized step to the learner while exporting a finer trace to the theorem prover?
