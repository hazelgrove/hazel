Hazel Thesis Proposal Implementation Roadmap

A standalone implementation plan derived from /Users/nishant/Downloads/nishant-thesis-proposal-document.pdf. Use this document across worktrees to align stepper architecture, mathematical capabilities, proof export, and target case studies.

Goal Exploratory engineering math in Hazel with machine-checkable export.
Users Engineers and students who know the math but not prover syntax.
Core Risk Automation that hides too much or exports untrusted large steps.
Near Term Coq-checked proof search for arithmetic, algebra, and trigonometry.

Research Target

The proposal extends Hazel Prover from classroom equational and inductive reasoning toward exploratory engineering mathematics. The intended workflow is not a CAS transcript and not raw theorem-prover scripting. It is a Hazel-native, selection-driven derivation interface where users take meaningful symbolic steps, the checker validates those steps, and completed traces can be exported to Coq/Rocq now, with Lean kept as the next prover backend target.

The implementation standard is skeptical certification: Hazel may use automation to propose or validate steps, but the exported artifact should contain enough trace information for an external prover to check the result independently.

Design Criteria From The Proposal

Criterion Implementation Consequence What To Avoid
Low setup cost Users should solve representative tasks inside Hazel without learning Lean/Rocq syntax first. Prover-specific details belong in export metadata and generated artifacts. UI flows that require users to pick prover lemmas directly.
Low interaction overhead Common rewrites, substitution, differentiation, and evaluation should be available through contextual stepper controls or projectors. Forcing every associative/commutative microstep by hand.
Appropriate step granularity Support one-step, checked multi-step, and automatic modes per exercise or stepper invocation. The chosen mode should be clear to the user before they start. Black-box full-expression simplification with no visible trace.
Mathematical coverage Every new rewrite group or operation should map back to one of the proposal case studies. Building generic symbolic features without a target workflow.
Trust and verification Accepted steps should store structured justifications, rule ids, selected subterms, and prover hints. Persisting only a display string such as arithmetic.

Mathematical Capability Ladder

Each level should include all previous levels. The UI can expose the selected level, but the implementation should enforce it through allowed rewrite groups and operation availability.

Level Capabilities Checker/Normalizer Shape Export Shape
Arithmetic and affine algebra Constants, variables, addition, subtraction, negation, and constant multiplication. Affine normal form with sorted variable coefficients and folded constants. Reassociate, commute, fold constants, scale terms, collect like terms.
Algebraic distribution Distribution, factoring, simple powers, FOIL, and medium-grain expansion choices. Polynomial normal form or named rewrite search over algebra rules. Small distribution/factor lemmas, with optional ring fallback only for debugging.
Trigonometric identities Pythagorean identities, sum/difference formulas, double-angle formulas, cofunction/reflection identities, negative-angle identities, and curated bidirectional identities. Rule database filtered by syntactic match, active math level, explicit preconditions, and export availability. Identity lemma references in Coq/Rocq now, with Lean mappings retained in rule metadata and every accepted trig fixture checked by generated proof scripts.
Functions and calculus Function expressions, symbolic differentiation, product rule, chain rule, integration hooks, and evaluation at a point. Operation-specific proof-producing transformations rather than only equivalence normalizers. Derivative rule lemmas and generated equality obligations.
Taylor workflows Repeated derivatives, substitution, evaluation, and polynomial assembly. Compound derivation trace built from calculus and evaluation subtraces. Sequence of derivative/evaluation lemmas plus assembly steps.
Inequalities Bounds, equality/inequality chains, monotonicity, absolute values, and theorem applications such as mean value theorem. New relation-chain representation; equality-only replacement is insufficient. Ordered relation transitivity and named bound lemmas.
Linear algebra and Jacobians Matrix/vector expressions, elementwise symbolic operations, Jacobian construction, and equilibrium substitution. Matrix entries as Hazel expressions with elementwise operation traces. Matrix extensionality plus exported traces for each cell.

Math Group Specification Matrix

This table captures the central part of the whiteboard sketch, not every surrounding note. The key design split is that each math group has two commitments: the forms/objects Hazel can recognize, and the operations, rewrites, or tactics Hazel is allowed to apply to those forms. This table should guide future Axioms.re entries, checker normalizers, UI operation menus, and theorem-prover export records.

Group Forms/Objects Operations/Rewrites Automation/Tactics Export Notes
Arithmetic Integer, natural, signed-integer, and future float literals; affine terms over variables. Associativity, commutativity, additive identity, additive inverse, constant folding, and constant scaling. Simplify selected arithmetic, compare affine normal forms, and eventually expand each normalization phase into visible hidden steps. Current pilot group. Export should prefer small rewrites and use norm_num or ring-style tactics only as collapsed fallback policy.
Algebra Free variables, sums, products, powers, polynomials, and later rational expressions. Distribution, factoring, FOIL-style expansion, collection of like terms, cancellation with side conditions, and polynomial normalization. User-selected expand/factor operations, multi-step normal-form checks, and bounded rewrite search over named algebra rules. Should include arithmetic automatically. Avoid accepting broad algebraic equality unless the normalizer can emit an exportable trace.
Trigonometry sin, cos, tan, powers of trig terms, and angle expressions. Pythagorean identities, double-angle identities, angle-sum identities, cofunction/reflection identities, negative-angle identities, and curated bidirectional substitutions. Identity menu filtered by selected expression; optional direction choice when a rule can rewrite both ways; bounded proof search for the supported identity families. Prefer explicit identity lemma references. Do not hide the choice of identity inside a generic simplify tactic. Current generated Coq fixtures cover the core supported trig identities.
Calculus Derivatives, integrals, limits, substitutions, function applications, and expressions such as d/dx (sin(x^2)). Derivative rules for constants, variables, polynomials, trig functions, product rule, chain rule, substitution/evaluation at a point, and later integration rules. Auto-differentiate a selected subterm, request one named rule, or produce a compound hidden trace for Taylor-style workflows. This is operation-oriented, not just equality normalization: exported traces must preserve the chosen calculus rule and any generated side obligations.
Programming-Language Forms Well-typed terms from the Hazel grammar: variables, functions, applications, conditionals, pattern matches, lists, tuples, and typed holes. Beta reduction, unfolding, substitution, case splitting, function-body expansion, list rewrites such as map/fold, and selected evaluator steps. Same three automation modes as math groups: one visible step, checked multi-step result, or auto-evaluation over an allowed operation set. Must respect typing and holes. Export likely needs a language semantics or theorem-prover encoding before broad automation is trustworthy.
Linear Algebra Vectors, matrices, Jacobians, indexed entries, matrix-vector products, and equilibrium substitutions. Elementwise simplification, matrix extensionality, Jacobian construction, substitution into entries, and linear solve or eigenvalue hooks later. Apply scalar math groups inside cells, build Jacobian rows and columns, and validate matrix equality by entrywise traces. Need explicit non-commutativity policy. Matrix export should reduce to cell-level proof traces plus structural matrix lemmas.
The implementation direction is cumulative: selecting a later row includes the rows above it when mathematically valid. For example, calculus automation can use arithmetic, algebra, and trig rules inside a derivative trace, but each hidden step must still name the group and rule that justified it.

Automation Modes

These modes should apply at the exercise or stepper invocation level. They are not independent mathematical levels; they control how much assistance is available within the selected level.

One Step User takes one visible Hazel/proof step. Useful for learning, transfer, and exercises that should mirror paper proof structure.
Check Result User writes a proposed next expression. Hazel checks whether both sides have the same normal form or proof-producing equivalence.
Auto Simplify Hazel applies an allowed operation or rewrite group and inserts the result, preserving the hidden proof trace for inspection/export.

Automation Depth Ladder

The top-right whiteboard sketch also separates automation by depth. This is the operational version of the UI's manual/check/auto choice: it describes how far Hazel is allowed to search or compress hidden steps once a math group is selected.

Depth Meaning User Experience Trace Requirement
Auto 0 One primitive step. Hazel applies a single evaluator step or a single named rewrite. Closest to manual stepping; useful for teaching the exact next rule and for debugging proof traces. One rule id, one focused before/after expression, one prover hint.
Auto 1 Local simplification. Hazel may combine a small fixed family of primitive rewrites into one visible step. User can select a subterm such as 1 + 2 + x and get the obvious local result such as x + 3. Ordered hidden trace, usually within one rewrite group such as arithmetic.
Auto 2 Bounded tactic or proof search over a chosen group. Hazel can try several rewrite paths or normalization phases. User gets help with medium-grain algebra/trig/calculus moves, but the search space is still constrained by the selected group. Search result must be replayable as phase traces; failed search should not change the expression.
Auto Max Exploratory automation. Hazel may use all allowed groups at the selected math level to propose or complete a larger derivation. Useful for exploration, examples, and checking answers; less appropriate when the exercise goal is practicing each rule. Must be explicitly marked as collapsed or expanded. Export can only trust it if the hidden trace can be replayed or discharged by an approved theorem-prover policy.

Near-Term Implementation Focus

The immediate engineering target is to get as close as possible to useful arithmetic and algebra support. The later groups should stay in the architecture so the design does not hard-code arithmetic-only assumptions, but they do not need full implementation in this phase.

Priority Scope Implementation Goal Architectural Requirement
Now Arithmetic Finish affine arithmetic checks, selected-subterm auto simplify, side-specific traces, and prover-hint resolution. Keep arithmetic expressed as a named group with forms, rules, normalizer, automation depth, and export metadata.
Next Algebra Add polynomial-oriented forms and operations: distribution, factoring/FOIL, collection of like terms, cancellation where side conditions are explicit, and checked normal-form equality. Algebra should include arithmetic automatically and should plug into the same checker/trace/export interfaces rather than a separate special case.
Later Calculus, programming forms, linear algebra Leave as design targets and type/API extension points. Trig is no longer purely future work; calculus and later groups should reuse the trig proof-search/export shape. Ensure group registration, automation settings, trace records, and UI labels can represent these future domains without changing the core stepper contract.

Proof Trace And Export

A completed Hazel derivation is currently structured but informal. The roadmap requires making it machine-checkable by turning each accepted action into a proof trace. 

type proof_step = {
  before: Exp.t,
  after: Exp.t,
  rule: Axioms.rewrite_rule,
  focus: option(Id.t),
  prover_hint: option(Axioms.prover_hint),
};

type accepted_step = {
  user_from: Exp.t,
  user_to: Exp.t,
  normal_from: Exp.t,
  normal_to: Exp.t,
  trace_from: list(proof_step),
  trace_to: list(proof_step),
  export_policy: [ `Primitive | `Collapsed(string) | `NotExportable ],
};
Current State Needed Change
RewriteChecker.re validates affine equivalence and returns normal expressions plus side-specific rule ids. Upgrade side-specific rule ids into replayable derivations from source expression to normal expression.
WrittenStep.re stores a justification string plus an optional trace summary with normal expressions, rule ids, and exportability metadata. RewriteChecker.re can resolve those rule ids back to Axioms.re prover hints by side. Upgrade the trace summary into full structured accepted-step data with before/after proof steps.
CoqExport.re can generate coarse proof scripts. Translate proof steps through Axioms.re prover hints, using collapsed tactics only as explicit policy.
Do not route this through a CAS as the source of truth. CAS-style simplification creates steps that are too large to trust or export cleanly. Use Hazel-native normalizers and proof-producing operations.

Target Case Studies

Case Study Representative Task Acceptance Criteria
Algebraic distribution Expand (x + 1)^2 to x^2 + 2x + 1 through selected subexpression rewrites. Users can choose distribution steps, check written results, and export the trace without relying on a single ring proof.
Trigonometric identities Transform expressions involving sin^2(x), cos(2x), and cos(4x). The UI shows multiple applicable identities for a selected subterm and records the chosen identity in the trace.
Symbolic differentiation Differentiate x^3 * sin(x) using product and chain rules. A projector supports step-by-step and one-shot modes, and both produce the same exportable derivative trace.
Taylor series expansion Differentiate repeatedly, evaluate at x0, and assemble an approximation polynomial. Intermediate derivatives and evaluated coefficients are retained as inspectable steps; errors can be localized to an earlier derivative or substitution.
Inequality bounding Derive |sin(x) - sin(y)| <= |x - y| using mean value theorem and |cos(c)| <= 1. Hazel can represent a mixed equality/inequality chain and reject invalid bound direction changes.
Jacobian linearization Compute a 2x2 Jacobian matrix for a nonlinear system at an equilibrium. Matrix cells carry independent derivative/substitution traces; the full matrix result can be exported by cell extensionality.

Implementation Phases

  1. Stabilize arithmetic: convert affine checking into proof-producing normalization and persist accepted traces.
  2. Add algebra rule groups: distribution, factoring, and polynomial normal forms with selectable medium-grain rewrites.
  3. Add contextual identity menus: trigonometric rule database, matchers, preconditions, and prover hints.
  4. Build proof-producing operation projectors: differentiation first, then evaluate-at and Taylor workflows.
  5. Design relation chains for inequalities and bounding rules.
  6. Add matrix/vector expression support and Jacobian-specific workflows.
  7. Harden export: choose initial target prover, map rules to library lemmas, and add tests that generated proof scripts check.

Reusable Guidance For Agents

  • Before implementing a math feature, identify which proposal case study it unlocks or improves.
  • Prefer Hazel-native proof-producing transformations over CAS calls.
  • Keep automation policy explicit in the UI and in serialized stepper state.
  • Treat Axioms.re as the registry for named rewrite groups and prover mappings.
  • When adding accepted-step behavior, store structured proof data first and derive UI labels from it.
  • Run make after every code or documentation edit.
