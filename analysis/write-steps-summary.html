Write Steps Branch Summary

The write-steps branch changes proof stepping from a mostly click-driven evaluator-step workflow into a mode where learners can type the next expression themselves. The important recent change is that typed steps are checked by comparing normalized meanings, not by requiring the exact left-associated evaluator step.

Written steps New proof step kind stores the user replacement and justification.
Normalization Checkers normalize both sides, then compare normal forms.
Arithmetic first Affine arithmetic is checked with a Hazel-native normal form.

What Is New

  • A new WrittenStep step kind can replace an expression in the proof with a user-entered expression and keep the generated justification text.
  • MissingStep now offers a write-out UI: "From: ... Take a step to: ..." with an inline Hazel editor.
  • A new setting, evaluation.write_out_steps, can be toggled globally and forced per theorem exercise.
  • The reverse-reverse theorem exercise opts into write-out steps.
  • The proof-step overlay can highlight a selected expression without fully activating the editor.
  • Semantic equality gained fixpoint-unrolling support for cases where evaluation and equality need to compare recursive definitions.

Old Written-Step Check

Previously, the written-step checker took the selected expression e1, asked the stepper for its available next evaluation steps, applied each candidate step, consumed automatic steps, and then checked whether the user's expression e2 exactly matched one of those results under semantic equality. 

get_next_exps(e1)
  |> find result where semantic_equal(result, e2)

That made valid algebraic rewrites too rigid. For example, the user could be forced into the evaluator's left-associative path: 1 + 2 + 3 to 3 + 3, rather than another mathematically equivalent expression.

New Written-Step Check

The current checker treats validation as a small pipeline: choose a checker, normalize both expressions with that checker, then compare the normal forms. This is intentionally extensible so more proof domains can be added later without rewriting the UI or WrittenStep storage model.

1. Input The selected expression and the user-entered expression are already elaborated and environment-substituted by MissingStep.
2. Normalize A checker maps each expression to a domain-specific normal form.
3. Compare The checker compares the two normal forms with its own equivalence relation.
4. Justify A successful checker returns the displayed justification, such as arithmetic. 
type normal_form =
  | Evaluated(Exp.t)
  | Affine(affine);

type checker = {
  justification: string,
  normalize: (~settings, ~env, Exp.t) => option(normal_form),
  equivalent: (normal_form, normal_form) => bool,
};

Arithmetic Normalization

The first checker is now affine_checker. It is Hazel-native and handles a limited affine arithmetic fragment over integer-like constants and variables.

  1. Strip dynamic ascriptions with DHExp.strip_ascriptions.
  2. Consume hidden automatic stepper transitions with take_auto_steps.
  3. Convert supported Hazel arithmetic into an Affine normal form: a constant plus sorted symbolic coefficients.
  4. Compare the two affine normal forms structurally. 
1 + 2 + 3  ==  3 + 3
x + 3      ==  3 + x
(x + 1)+2  ==  x + 3
2 * x + 3  ==  x + x + 3
x + 3 - x  ==  3

This means the written proof step does not need to follow Hazel's left-associated evaluator path as long as both sides are algebraically equivalent in this supported arithmetic fragment.

Algebrite is no longer part of written-step arithmetic validation. The checker accepts only what the Hazel-native affine normalizer can represent.

Third Step: Hazel-Native Affine Checker

The latest implementation replaces the Algebrite-backed arithmetic checker with a small Hazel-native normalizer. This is the first step toward theorem-prover export because the accepted arithmetic fragment is explicit and can later be paired with rewrite traces. 

type affine = {
  constant: Bigint.t,
  terms: list((string, Bigint.t)),
};

The normalizer currently supports:

  • integer, natural, and signed-integer constants,
  • variables as symbolic terms,
  • addition and subtraction,
  • unary minus for signed/integer expressions,
  • multiplication when at least one side is a constant affine form,
  • combining like terms and sorting variables by name.

It deliberately rejects non-affine symbolic multiplication such as x * x. Unsupported expressions return None and fall through to the bounded evaluation checker.

This still validates by comparing normal forms. Successful written steps now preserve an export-oriented trace summary with the checker label, rewrite group, each side's normal expression, side-specific rule ids, combined rule ids, and exportability flag. The next export-oriented bridge resolves those persisted rule ids back to Axioms.re rules and prover hints by side; after that, the remaining work is to replace those rule summaries with replayable before/after proof steps.

New quick tests cover 3 + x = x + 3, (1 + 2) + x = x + 3, 2 * x + 3 = x + x + 3, x * x != x + x, and x + 3 - x = 3.

Selected-Range Auto Eval

The newest code path adds an Auto Eval action to the missing-step overlay. It is meant for exploratory proof editing: a user can select a valid expression node, or a range that reparenthesization can turn into a valid expression node, and ask Hazel to simplify that selected subterm using the same Hazel-native affine arithmetic normalizer.

1. Select The overlay uses the current selected expression. If the selected range is not already a node, it first asks the reparenthesizer for a version of the expression where the range is represented as a node.
2. Simplify RewriteChecker.simplify_arithmetic normalizes the selected expression to affine form, then reifies that form back into a Hazel expression.
3. Replace The simplified subterm is inserted back into the full expression by expression id.
4. Step StepperBase stores this as an AutoSimplifyStep, so undo, persistence, and stale-step invalidation follow the same stepper machinery as other proof steps. 
1 + 2 + x              Auto Eval  x + 3
 whole expression:
1 + 2 + x + x + 4 + x + 3
                          Auto Eval  3 * x + 10

The action only appears when the simplifier can produce a changed expression. Non-affine selections such as x * x, expressions containing holes, and unsupported programming forms should fail closed rather than making a proof step.

Implementation plan

Rows should be cumulative. Selecting Algebra should allow every arithmetic rewrite plus algebra-specific rewrites; selecting a later row should include every row above it. Columns then control how much automation Hazel applies with that allowed rewrite set. 

allowed_groups(level) =
  rewrite_groups
  |> filter(group => group.rank <= level.rank)
Selected level Allowed rewrite groups Example use
Arithmetic arithmetic Fold constants, commute addition, collect affine terms.
Algebra arithmetic + algebra Use arithmetic while distributing, factoring, or cancelling.
Functions/lists arithmetic + algebra + functions/lists Use numeric simplification inside unfold, beta, map, and fold rewrites.
Calculus all earlier groups + calculus Use arithmetic and algebra inside domain-specific derivative or limit rules.

The intended traversal is left to right within a row, then top to bottom across rows: manual arithmetic, checked arithmetic, automatic arithmetic; manual algebra, checked algebra, automatic algebra; and so on. The UI should still expose this as two controls rather than one long list: 

Math level:  Arithmetic | Algebra | Functions/lists | Calculus
Automation:  Manual | Check result | Auto eval

Implementation work should move in this order:

  1. Extend Axioms.re so each rewrite group has a stable rank, a level label, prover hints, and explicit rule ids.
  2. Add a helper such as allowed_groups(level) and route RewriteChecker through that helper instead of hardcoding arithmetic.
  3. Split the UI state into rewrite_level and automation_stage. The current arithmetic checker becomes Arithmetic + Check result; selected-range simplification becomes Arithmetic + Auto eval.
  4. Make successful checks and automatic steps return a concrete trace: not just algebra, but the rule sequence such as add_assoc, add_comm, const_fold, distrib, and collect_like_terms.
  5. Use the selected level to bound future proof search. For example, Algebra + Auto eval may use arithmetic and algebra tactics, but it should not silently use function/list or calculus rewrites.

Current checker behavior

The checker now has level-aware entry points, but only arithmetic has real rewrite rules today. The active APIs are: 

check_written_step_at_level(~level, ...)
check_rewrite_at_level(~level, ...)
check_rewrite_result_at_level(~level, ...)

These functions use allowed_groups(level) to choose which rewrite groups are available. The rule catalog now has arithmetic and algebra groups, arithmetic has executable affine checking, and Algebra now has a deliberately small distribution/factoring checker. Algebra is enabled as WIP for testing, but it is still not a full polynomial normalizer.

Selected level Allowed groups today Practical effect today
Arithmetic arithmetic Accept affine arithmetic equivalence and concrete evaluation equality.
Algebra arithmetic + algebra Accepts direct distribution and reverse distribution/factoring such as x * (y + z) == x * y + x * z. Still narrow and WIP.
Functions/lists arithmetic + algebra Future level only; no function/list rewrite group is implemented yet.
Calculus arithmetic + algebra Future level only; no calculus rewrite group is implemented yet.

The current arithmetic checker accepts examples such as 3 + x == x + 3, (1 + 2) + x == x + 3, 2 * x + 3 == x + x + 3, and x + 3 - x == 3. It rejects non-affine symbolic forms such as x * x, (x + 1) * (x + 2), and unknown programming forms such as f(x) + 3. The current Algebra checker now uses a small polynomial normal form for Check result: it expands products over sums, multiplies monomials, folds coefficients, collects like terms, and supports small integer powers such as x ** 2. Examples such as (x + 1) * (x + 2) == x * x + 3 * x + 2 are accepted at Algebra level but still rejected at Arithmetic level.

Manual One Step now has two paths. It first checks for a strict exportable arithmetic rewrite: one adjacent swap in a flattened addition chain, recorded as arith.add_comm, or one adjacent constant fold in a flattened addition chain, recorded as arith.const_fold. This intentionally abstracts over association for examples such as 1 + 2 + 3 + 4 -> 1 + 5 + 4 and 1 + 2 + 3 + 4 -> 1 + 2 + 7, while still rejecting changes that require multiple visible arithmetic operations. If no strict rule matches, it falls back to the original write-steps evaluator-step checker and records that result as non-exportable until evaluator transitions are mapped to trusted rule ids.

  • Generalize beyond the current two-product distribution/factoring shapes: nested distribution, multi-term sums, coefficients, repeated common factors, and canonical ordering. Broader replayable hidden traces are still needed.
  • Decide which associativity and commutativity moves can stay hidden in One Step and which must become explicit proof trace entries for theorem-prover export.

Open level-design question

The next design decision is what each level should mean. There are at least three plausible interpretations for Algebra:

Algebra interpretation Would allow Tradeoff
Ring-normalization level Polynomial equivalence such as (x + 1) * (x + 2) == x * x + 3 * x + 2. Powerful, but needs a trusted ring-normalization trace/export story.
Named-rule level Explicit laws such as a * (b + c) == a * b + a * c. More theorem-prover friendly, but weaker unless Hazel adds bounded proof search over rules.
Equation-solving level Proposition transformations such as x + 3 = 10 to x = 7. Useful, but different from expression rewriting because it transforms equations/propositions rather than just terms.
Working default: keep Arithmetic conservative and affine. Decide whether Algebra should mean ring normalization, named algebraic laws, equation manipulation, or a staged combination of those.

Evaluation Normalization

The fallback checker is evaluation_checker. It evaluates both expressions with Evaluator.evaluate_and_limit using a bounded step limit, strips ascriptions from the resulting values, and compares those values with Hazel semantic equality. 

normalize_by_evaluation(e) =
  Evaluator.evaluate_and_limit(~env, ~step_limit=1000, e)
  |> value
  |> DHExp.strip_ascriptions
  |> Evaluated

This handles cases where both expressions compute to the same concrete Hazel value. It is deliberately bounded, so nonterminating or very large computations fail closed rather than hanging the checker.

How Evaluation Fits In

Hazel has two related evaluation mechanisms here:

  • EvaluatorStep.get_status and EvaluatorStep.take_step expose individual visible or automatic stepper transitions for the interactive proof UI.
  • Evaluator.evaluate_and_limit runs the evaluator to a final value, subject to a step limit.

The old written-step checker relied on the first mechanism and matched exactly one visible next step. The new checker can still consume hidden automatic steps during arithmetic normalization, but the main validity question is now semantic: do the selected expression and the typed expression normalize to equivalent forms?

Extension Points

To add a richer proof domain later, add another checker value and include it in written_step_checkers. A checker can define its own normal form and equivalence strategy by extending the normal_form variant and implementing:

  • a domain-specific normalize function,
  • a domain-specific equivalent relation,
  • a short justification string for the proof UI.
Good future candidates are list algebra, tuple projection/extension laws, induction hypothesis rewriting, and theorem/assumption based rewriting.

Current Limitations

  • The Hazel-native arithmetic checker is currently affine, so it does not accept nonlinear symbolic expressions such as x * x.
  • The fallback evaluator compares final values, so it is useful for computations but not for symbolic equivalence that does not evaluate to a concrete shared value.
  • The checker accepts broad equivalence for written steps. If an exercise needs single-step discipline, it may need a stricter checker or per-exercise policy.
  • Written steps now store a trace summary, but the displayed justification is still checker-level (arithmetic or same evaluated result), not a detailed derivation of the normalization process.
  • Auto Eval currently reifies a canonical affine result, but it does not yet expose or persist the hidden rewrite sequence needed for a theorem prover.

Todos

  • Add quick tests for selected-subterm simplification through AutoSimplifyStep, including stale-step invalidation when the original expression changes.
  • Add integration coverage for reparenthesized selected ranges, since those are the selections most likely to miss real AST-node boundaries.
  • Obscure left-associativity artifacts entirely in the proof UI. A reparenthesized selected range should feel like one natural selection: no separate green evaluator-step highlight, no user-facing distinction between "Step" and "Step Here", and no extra displayed parentheses such as (4 + x) when the source range was written as 4 + x.
  • Decide whether the normalizer should preserve more source shape or always emit canonical grouped terms such as 3 * x + 10.

Thesis Proposal Roadmap

Canonical standalone roadmap: analysis/thesis-proposal-roadmap.html. This section is the compact in-branch copy.

Source: /Users/nishant/Downloads/nishant-thesis-proposal-document.pdf. The proposed research frames this branch as one part of a larger Hazel Prover extension: an exploratory engineering-math interface where users can manipulate symbolic derivations in Hazel and export completed step traces to a full theorem prover such as Lean or Rocq.

Big Picture Goal

Hazel should support rigorous symbolic work by practitioners who are comfortable with engineering mathematics but not necessarily with proof assistant syntax. The interface should preserve the current paper-like, selection-driven proof workflow while adding enough automation to reduce bookkeeping without hiding reasoning steps that matter for learning, trust, or theorem-prover export.

Selectable step granularity Keep the exercise-level automation mode: one visible step, checked multi-step equivalence, or automatic simplification. Each mode should be available per math level rather than chosen independently for every step.
Curated rule groups Grow Axioms.re from arithmetic metadata into a database of named rewrite groups: algebra, trigonometry, functions, calculus, inequalities, and linear algebra. Each rule needs applicability information and prover mappings.

Evaluation Signals To Preserve

  • Low setup cost: users should begin solving representative tasks without learning theorem-prover syntax first.
  • Low interaction overhead: routine rewrites, differentiation, and substitution should not require excessive clicking or typing.
  • Step granularity: automation should avoid both full-expression black-box simplification and tiny bookkeeping-only rewrites.
  • Mathematical coverage: every new implementation slice should map back to at least one proposal case study.
  • Trust and verification: accepted Hazel steps should be inspectable and eventually exportable as machine-checkable proof obligations.

Theorem Prover Trace Plan

The current arithmetic normalizer is good enough to decide whether two affine expressions are equivalent, but it is not yet a proof object. It canonicalizes both expressions into maps of constants and variable coefficients, then compares those normal forms. For theorem prover export, we should keep that normal form as the planner, but also emit a replayable derivation from each original expression to the shared normal form.

Target Shape

type proof_step = {
  before: Exp.t,
  after: Exp.t,
  rule: Axioms.rewrite_rule,
  focus: option(Id.t),
  backend_hints: list(Axioms.prover_hint),
};

type normalization_proof = {
  original: Exp.t,
  normal: Exp.t,
  steps: list(proof_step),
};

A successful written step should eventually store a normalization_proof, not only a justification string such as arithmetic. For e1 == e2, the checker should produce two traces:

  1. e1 = normal_form
  2. e2 = normal_form

The exporter can then combine those traces to prove e1 = e2 by transitivity and symmetry.

Arithmetic Pipeline

The first version should keep the affine-map checker for validation, then generate a structured trace by phase:

  1. Reassociate additions into a predictable tree shape.
  2. Push subtraction and negation into coefficients.
  3. Normalize constant multiplications such as 2 * x.
  4. Sort terms using adjacent commutativity swaps.
  5. Collect adjacent like terms.
  6. Fold constants.
  7. Rebuild the canonical expression.
Axioms.re should remain the source of truth for rewrite rule names, groups, and prover hints. RewriteChecker.re should perform normalization and return a prover-agnostic Hazel trace. The stepper should store that trace. CoqExport.re, RocqExport.re, and a future LeanExport.re should be backend renderers over the same proof steps, not separate checker implementations.

Current Search And Export Flow

The standalone Proof Search target calls AxiomSearch.search. The search takes a source expression, target expression, rewrite level, max depth, and allowed rule ids. It tries bounded local rewrites from Axioms.re, walking the AST and recording each successful rewrite as a prover_step with the rule id, full before/after expression, local redex before/after expression, occurrence, and detail string.

Search currently supports small arithmetic and algebra examples such as constant folding, addition associativity/commutativity, distribution, and factoring. Small addition-chain permutations use a target-guided macro rule, arith.reorder_add_terms, rather than brute-forcing every add_assoc/add_comm path. That macro should eventually lower to primitive prover rewrites.

The UI path is debounced live: after the user stops editing the target for roughly 500ms, Hazel runs proof search once. Search is skipped for holes, and the manual Run Proof Search button remains available while waiting or after an invalid result. Once search is valid, the box shows Replace. 

Proof Search target
  -> AxiomSearch.search
  -> AxiomSearch.trace_summary
  -> WrittenStep stored in the stepper trace
  -> StepperBase.export_coq
  -> CoqProofExport assertion replay
  -> coq-export-YYYYMMDD-HHMMSS.v

window.HazelJSCoq exists as a lazy browser-side JSCoq bridge, but it is not the active checker yet. Today the trusted check is still external coqc on the downloaded file. The next JSCoq step is to send the generated Coq text to that bridge and report success/failure in Hazel.

Exporter Policy

Large tactics such as ring, ring_nf, and norm_num are too coarse to be the trusted export format. They can be useful for local debugging or comparison, but exported proofs should prefer small named rewrites, using prover metadata attached to Axioms.re rules such as arith.add_assoc, arith.add_comm, arith.const_fold, and arith.collect_like_terms.

The current Coq/Rocq demo emits named prover assertions for each recorded Hazel prover step, then rewrites with those assertions. The tiny arithmetic cases still use cbn inside the local assertion proof when the obligation is closed arithmetic, but the surrounding proof now has the right shape: one named fact per Hazel breadcrumb, followed by a replay step that uses those facts. Symbolic affine arithmetic currently uses an explicit temporary lia fallback while the normalizer grows finer local breadcrumbs. Simple algebraic distributivity does not use ring; it exports the local redex, an additive occurrence index, and a small rewrite script over distributivity.

Downloaded Coq files now use compact Coq-safe names such as coq-export-20260615-103245.v, avoiding browser duplicate filenames like stepper_coq_export (2).v that Coq refuses as module names.

Unified Planner Plan

This plan unifies proof search, normalization, and math levels around one invariant: every accepted automated step must either carry replayable proof breadcrumbs or be explicitly marked as a macro step that can be lowered into primitive prover rewrites. Normalization becomes a proof planner, not a black-box equivalence oracle.

Shared Proof Planning Model

  • Introduce one internal proof-planning result used by normalization, proof search, check-result, and auto-simplify.
  • The result should include source expression, target expression, accepted math level, visible or macro rule ids, primitive prover_step breadcrumbs when available, and export status.
  • Export status should distinguish primitive replayable steps, macro steps that need lowering, and explicitly non-exportable fallback paths.
  • Keep Axioms.re as the source of truth for math level/group membership, rule ids, labels, prover hints, and whether a rule is primitive or macro/lowered.

Normalization As Exportable Planning

  • Replace "normalize both sides and compare" with: source -> normal, target -> normal, then compare normal forms and export by replaying both traces.
  • Arithmetic normalization should record steps for flatten/reassociate addition, AC reordering, constant folding, like-term collection, and coefficient scaling.
  • Algebra normalization should build on arithmetic and add distribution, factoring, cancellation, polynomial expansion, and polynomial collection.
  • Do not use a normalizer result as exportable unless it emits primitive steps or emits a macro with a known lowering plan.

Proof Search Role

  • Keep bounded proof search for local transformations and examples where the rewrite path is short.
  • Do not use raw search for large AC rearrangements; use target-guided normalization or macros instead.
  • Generalize arith.reorder_add_terms into an AC reorder macro family that records operator, source term order, target term order, and basis rules.
  • Enable multiplication reorder only after coefficient collection and distribution interactions are handled deliberately.

Math Level Integration

  • Levels stay cumulative: Algebra includes Arithmetic, and future levels include all lower levels.
  • Each level exposes the same stages: One Step, Check Result, and Auto Simplify.
  • One Step should allow one visible primitive step or an approved macro step. Check Result should compare proof-planned normal forms. Auto Simplify should apply the level's default normalization plan.
  • Proof Search remains a prototype target for now, but it should call the same planner/search backend used by future automation stages.
  • Longer term, a "math level" should be a user-selectable automation profile rather than a fixed enum. A profile should declare the mathematical structures in scope, such as integers, floats, real variables, trigonometric functions, AST terms, or program values, plus the rewrite families that are allowed, such as associativity, commutativity, distribution, differentiation, beta-reduction, or trig identities.
  • Associativity and commutativity must remain profile-controlled capabilities. Arithmetic and trigonometry profiles can opt into AC-normalization macros such as arith.reorder_mul_factors, while a programming-language/AST profile can omit those macros so left-associative syntax remains explicit and user-visible.

Test Plan

  • Unit tests should cover arithmetic AC reorder, arithmetic check-result trace status, algebra distribution occurrence, macro export status, and non-exportable fallback paths.
  • Coq tests should keep the existing fixture checks and add AC reorder once its macro lowering is implemented.
  • UI smoke tests should cover debounced Proof Search, hole-skipping, valid Replace behavior, and the sidebar outline links.

Assumptions

  • Exportability is a hard design constraint: normalization must not silently accept steps that cannot eventually be justified by recorded rules.
  • Macro proof steps are acceptable for v1 only when explicitly labeled and paired with a planned primitive lowering.
  • JSCoq remains scaffolded only; coqc is the trusted checker until browser checking is wired into the export flow.
