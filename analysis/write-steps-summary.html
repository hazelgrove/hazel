Hazel Write Steps Implementation Summary

This document is the current implementation map for write-steps, math automation, Algebrite suggestions, and Coq/Rocq export. The long historical roadmap was intentionally removed; the standalone thesis roadmap remains in analysis/thesis-proposal-roadmap.html.

Typed steps Users can write the next expression and have Hazel check it.
Profile-gated math Arithmetic, Algebra, and Trigonometry are editable presets.
Export traces Accepted steps carry prover-oriented summaries when available.

Current State

The branch turns the missing-step overlay into a small math workbench: choose a math level, choose an automation stage, write or select a candidate step, then store a proof step with a justification and export metadata.

  • WrittenStep, rewrite suggestions, auto simplifications, and proof-search candidates all flow through the same stepper replacement path.
  • Axioms.re is the source of truth for math levels, automation stages, rewrite groups, rule ids, operation display metadata, step policies, and Rocq tactic plans.
  • RewriteChecker.re owns normalization, equivalence checks, profile-aware one-step validation, trace summaries, and prover-step breadcrumbs.
  • ProfileBoard.re is the current proof-of-concept customization surface. It starts from the selected built-in profile and stores in-memory visible-operation toggles plus profile-level cleanup toggles.
  • Coq/Rocq export replays stored prover steps where they exist and falls back to labeled tactic groups for coarser proof-search macros.
Historical note: the earliest written-step checker only compared against Hazel evaluator next steps. The current checker is level-aware and can accept normal-form equivalence, guarded rewrite targets, or bounded Rocq search results.

Profiles And Custom Math Modes

Math modes are now best understood as profiles. A built-in mode such as Arithmetic, Algebra, or Trigonometry is a preset profile with a checked set of visible operations, profile-level cleanup toggles, examples, and prover plans. A future user-defined math mode should be the same kind of profile document with different choices.

Layer Current implementation Intended customization path
Operation catalog Axioms.operation_metadata records stable ids, natural-language names, short labels such as Comm +, and examples such as 1 + 2 = 2 + 1. Use this metadata as the UI-facing registry for all built-in and verified custom operations.
Visible step policy step_policy.visible_rules declares which named operations count as student-visible steps and which cleanup capabilities each operation is allowed to tolerate. The active profile then applies global cleanup toggles across those per-operation guardrails. Let instructors and users enable/disable operations, adjust profile-level cleanup, and choose whether operations are one-step or repeatable once repeat semantics are implemented.
Profile board The Profile button opens a modal that renders generated controls from the selected profile. Overrides are currently in-memory and keyed by visible operation id or cleanup capability id. Persist the same override object as a course/user profile, support import/export, and attach selected profiles to assignments or scratchpads.
Validation Arithmetic, algebra, and trigonometry one-step checks now read the active profile. Disabling a visible rule removes that rule from profile-aware validation. Route written-step checking, proof search, browser JSCoq, and file export through the same resolved profile value.
Custom identities Not implemented as user input yet. Built-in trig identities are cataloged and shown in Trigonometry profiles. Accept declarative equations, verify them with Rocq/JSCoq, then register verified identities as normal catalog operations with matcher/search/export support.
The stable ids remain internal and prover-facing. The profile UI should show names, short labels, examples, and explanatory mode text such as Counts as one step, not raw ids like alg.distribute_mul_add or implementation labels like once.

Unified Rule Plans

The desired end state is one profile execution plan shared by Hazel checking, browser JSCoq/Rocq validation, file export, and the UI. The current code is moving in this direction, but one-step matching and Rocq tactic plans are still only partially unified.

Concept Design Current status
Rule catalog Each rule should have a stable id, display metadata, level, direction, Hazel matcher or normalizer, Rocq lemma/tactic atom, and optional cleanup classification. Rule ids, display metadata, cleanup capabilities, and Rocq tactic-plan atoms exist. Hazel matchers are still mostly hand-wired in RewriteChecker.re.
One Step Apply exactly one student-visible operation, with permitted cleanup before/after or modulo comparison. This is one visible math move, not one primitive rewrite. Works for the main arithmetic/algebra/trig cases, including profile-aware visible-rule toggles and global cleanup toggles. The execution engine is not yet generic over all catalog rules.
Check Result Search or normalize with many allowed profile rules, using the same rule set as One Step but a different application policy: bounded search, repeat, and optional finishers. Rocq tactic plans are purpose-specific, and the UI exposes Check Result. The Hazel and Rocq paths still need a shared stage-plan interpreter.
Auto Eval Run deterministic profile-approved simplification to produce Hazel's preferred next expression. Export should replay or certify the same rule plan. Auto simplification exists through current stepper paths, but it is not yet driven by the same declarative rule application plan as One Step and Check Result. 
profile
  -> stage plan
     -> Hazel checker/search
     -> Rocq tactic program
     -> UI controls
     -> export metadata

A stage plan should be a small sequence of phases. For example, an Algebra One Step plan can allow cleanup normalization, then exactly one visible rule such as distribution or factoring, then cleanup normalization again. Check Result can use the same rule catalog with bounded search or repeat-until-stuck policies. Auto Eval can use a deterministic repeat plan.

The key invariant should be: if Hazel accepts a One Step move using a profile rule, Rocq export should know which tactic atom or lemma certifies that same rule. If Rocq proves something broader, it may be acceptable for Check Result, but it should not silently become a One Step proof.

Checker Pipeline

The stepper separates the math level from the automation stage. The selected profile controls which objects, visible operations, cleanup capabilities, and prover plans are legal; the stage controls how much help Hazel provides.

One step Show explicit rewrite targets and manual actions for a selected expression.
Check result Compare the written target using the checker for the selected math level.
Auto simplify Offer local simplification targets that Hazel can justify.
Proof search Ask bounded JSCoq/Rocq tactic search to validate a candidate target. 
selected expression + user target
  -> selected built-in or custom profile
  -> construct gate and visible-rule policy in Axioms.re
  -> RewriteChecker normalizer, rewrite target, or profile-aware one-step rule
  -> trace_summary with rule ids, profile-sensitive cleanup, and prover_steps
  -> StepperBase stores the accepted proof step
  -> CoqProofExport replays or validates the trace

Math Levels

Built-in profiles are cumulative by rank. A higher profile can use lower-level operations, but export should still pick the smallest tactic group that matches the actual subgoal.

Level Status Allowed work Default Rocq group
Arithmetic Active Constants, affine terms, adjacent arithmetic steps, constant folds, and constant distribution as a one-step operation. hazel_arithmetic
Algebra Active Distribution, factoring, cancellation, AC cleanup around selected operations, and polynomial normal forms. hazel_algebra
Trigonometry Active Algebra profile operations plus cataloged sin/cos/tan identities such as Pythagorean, sum/difference, double-angle, half-angle, cofunction, reflection, and negative-angle rules. hazel_trigonometry
FunctionsAndLists Planned Unfold, beta, map, fold, and induction helpers. Not implemented
Calculus Planned Derivative, limit, and domain-specific theorem groups. Not implemented

Construct gating rejects expressions that require a higher level, such as trig calls in Arithmetic mode or unknown function calls before the Functions/lists level exists. Profile operation toggles additionally reject specific visible rewrites even when the expression is legal at the selected level.

Capabilities

Arithmetic

  • Affine normal form: constant plus sorted symbolic coefficients.
  • Accepts examples like 3 + x == x + 3 and 2 * x + 3 == x + x + 3.
  • Rejects non-affine symbolic products like x * x.
  • Manual one-step recognizes adjacent addition swaps and constant folds as exportable rules.

Algebra

  • Polynomial normal forms cover products over sums, small powers, coefficients, and like-term collection.
  • Rewrite targets cover distribution, reverse distribution/factoring, cancellation, binomial/trinomial expansion, conjugates, and completing simple squares.
  • Current weakness: some associativity/flattening behavior is still presentation-driven rather than a single canonical UI model.

Trigonometry

  • Bounded identity search covers selected sin/cos/tan transformations and double-angle style rewrites.
  • Algebra-only subgoals under trig expressions should export through the Algebra tactic group when trig calls are unchanged.
  • Scalar simplifications inside trig arguments, such as cos(2 * (2 * x)) -> cos(4 * x), are handled as prover-searchable steps.

Algebrite Status

Algebrite is not the trusted written-step arithmetic checker. It is currently used as a suggestion source and retained for legacy step compatibility.

  • The UI button is labeled simplify with algebrite and seeds the written target editor with one candidate simplification.
  • The candidate is checked by the same Hazel/Rocq path as if the user had typed it manually.
  • Export should depend on the accepted Hazel trace or Rocq tactic summary, not on trusting Algebrite.

Coq/Rocq Export

There are two related paths. Browser JSCoq validates candidate steps during editing. File export renders a complete Coq/Rocq proof from the stored stepper chain. A mismatch between these paths is a bug.

Part Role Current policy
ProofSearchBackend.re Builds bounded tactic-search programs. Chooses the export level from the subgoal, not only from the UI mode.
CoqExport.re Renders Hazel expressions into Coq/Rocq terms. Chooses integer or real prelude based on the whole proof context.
CoqProofExport.re Replays stored proof steps. Uses local assertions for breadcrumbs and labeled tactic fallbacks for macros.
window.HazelJSCoq Browser-side checker. Should reuse managers when possible, but cleanup must not crash JSCoq logging.
Export still contains coarse tactic fallbacks for some macro steps. The next quality bar is to lower more accepted UI actions into primitive prover breadcrumbs, especially algebra normalization and hidden associativity/commutativity steps.

Rocq tactic groups by math level

Math levels are the policy source of truth, but the exported tactic group is chosen from the actual checked subgoal. This matters when a Trigonometry-mode expression contains an algebra-only rewrite, such as distributing around unchanged cos(...) calls.

Effective level Macro rule id Rocq tactic group Current scope
Arithmetic rocq.arithmetic_tactic_search hazel_arithmetic Linear arithmetic, constant folds, simple numeric cleanup, and bounded rewrite search.
Algebra rocq.algebra_tactic_search hazel_algebra Arithmetic plus distribution, factoring, polynomial-style expansion, cancellation, and scalar-product simplification.
Trigonometry rocq.trigonometry_tactic_search hazel_trigonometry Algebra plus supported sin/cos identities, half-angle rules, double-angle rules, Pythagorean rules, and trig argument algebra.
FunctionsAndLists, Calculus Reserved macro ids Not active as user-facing groups These levels are disabled until they have their own rule groups, proof rules, and export tactics.

Per-step JSCoq checking and export automation

The intended flow is proof-producing even when the UI shows a single button press or a collapsed automation result.

  1. Axioms.re defines the cumulative math levels, automation stages, rewrite groups, rule ids, and prover hints.
  2. ProofSearchBackend.effective_level_for_request lowers a requested level to the smallest sound export group for the subgoal. In particular, Trigonometry and Calculus requests whose trig applications are preserved export as Algebra subgoals.
  3. ProofSearchBackend.rocq_search_program renders a one-theorem JSCoq/Rocq check with the inferred integer or real domain and the selected tactic group.
  4. If browser JSCoq accepts that theorem, Hazel stores a collapsed trace_summary with the macro rule id and a prover_step. Algebrite suggestions use the same path: Algebrite only proposes the target; Rocq/Hazel still validates it.
  5. File export replays stored prover_steps as local Coq/Rocq assertions, then rewrites them into the final theorem. When a step has no fine-grained breadcrumbs, export falls back to the recorded tactic group rather than guessing from the visible UI mode.
  6. Generic cleanup steps are domain-aware: integer cleanup uses the bounded integer rewrite fallback, while real cleanup uses hazel_arithmetic so facts like 2 * 1 = 2 in R do not fail export. 
selected source + candidate target
  -> Axioms level gate
  -> effective export level from the subgoal
  -> JSCoq theorem using hazel_arithmetic / hazel_algebra / hazel_trigonometry
  -> accepted trace_summary with rule ids and prover_steps
  -> CoqProofExport local assertions or tactic-group macro
  -> local coqc and browser JSCoq should agree

Known Gaps

  1. Profile editing is still an in-memory proof-of-concept. It does not yet persist custom math modes, import/export profile JSON, or attach a profile to an assignment.
  2. Repeatable visible-step modes are displayable but not generally interpreted by the Hazel one-step matcher. Current profile-aware validation is primarily one visible operation plus allowed cleanup.
  3. Cleanup capabilities are profile-aware in Hazel, but the Rocq certificate path does not yet replay each cleanup atom from the same catalog entry.
  4. Custom identities are not user-authored yet. Built-in identities have rule ids and metadata, but user identities need declaration, validation, matcher/search registration, and export support.
  5. Browser automation remains brittle in this repo because Playwright may be installed without a managed browser binary, and Chrome can fail under sandboxed execution. Treat local browser tests as useful but not currently dependable CI evidence.
